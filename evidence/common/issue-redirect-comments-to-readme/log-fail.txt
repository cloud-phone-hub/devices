## 第 2 节：为什么不能「直接删」——注释是产物的一部分

`05_build_vendor_boot` 的 `readAsset` 在 `from-device: redirect` 时调
`ModuleSection.RenderRedirect()`，而 `RedirectEntry` 是二选一结构：

```go
// internal/device/modules.go
type RedirectEntry struct {
    Comment *string      // 非 nil：一行注释/空行，原样输出
    Rule    *RedirectRule // 非 nil：一条规则，输出 "<type>  <from>  <to>"
}
```

所以数组里的字符串会被**原样写进** ramdisk 的 `lib/modules/cdh_redirect.rules`。
单测 `TestReadAssetRedirectFromDevice` 就是按这个断言写的：

```go
comment := "# ---- /vendor ----"
want := "# ---- /vendor ----\ndir  /vendor/etc  /mnt/vendorpatch/vendor/etc\n"
```

也就是说：这次改动会改变产物字节（配方号必然变化），不能当纯格式化提交。
被否掉的两个做法：

1. **只删注释、不留说明**：`.rules` 里的「为什么这么改」直接丢失。规则表本来就是
   「规则 + 理由」一起才可维护，删掉等于把知识扔了。改由机型 README 承接。
2. **给注释换字段名（如 `"comment": "..."`）**：仍是 JSON 数组里的非规则元素，
   遍历脚本照样要过滤，只是把字符串变成对象，可读性没改善。否。

## 第 3 节：本轮踩的四个坑

1. **`json.dump` 重写会造出整文件 diff**：第一版脚本打算 `json.load` → 删 → `json.dump`，
   会把 4 空格缩进、空行分布、`hardware` 数组的紧凑写法全部重排，13 份清单产生
   几千行无效 diff，评审无法确认「只删了注释」。改成**文本级按行删除**：定位
   `"redirect": [` 到匹配 `]` 的行区间，区间内只删 `^\s*"#`、`^\s*""` 与空行，
   其余字节原样保留。
2. **新建 README 第 3 行出现空代码块**：头部模板写的是
   `%s（`%s` / `%s`）` = `name（`device` / `board`）`，而 `oneplus/15r` 与
   `oneplus/ace3` 的 `device` 字段为空，生成出 `` （`` / `canoe`） `` 这种残句。
   已统一改成只保留有值的那一个（`（`canoe`）`）。
3. **`oriole` / `3a` 的 dry-run 直接 exit=1**：一度以为是我改坏了 JSON，实际是这两台
   各有多份清单（`baselines/` 下 4 份 / 2 份），`cdh device build` 要求 `--manifest`
   指定。加参数后正常——校验脚本要按设备实际清单数判断，不能只看返回码。
4. **`oppo/pme110` 没有 `modules` 段**：校验脚本第一版直接 `bd['modules']['redirect']`，
   在 pme110 上报 `KeyError: 'modules'`。它本来就没有 redirect 段（0 条规则），
   跳过即可；脚本改成 `.get('modules') or {}`。
