=== 2. mac_admin 是连带现象，不是根因（内核源码实锤） ===

security/selinux/hooks.c:3258 selinux_inode_setxattr()：
	rc = security_context_to_sid(value, size, &newsid, GFP_KERNEL);
	if (rc == -EINVAL) {
		if (!has_cap_mac_admin(true)) {       ← 类型查不到时才去要 CAP_MAC_ADMIN
			... audit_log_format(ab, "op=setxattr invalid_context=");
			return rc;
		}
		rc = security_context_to_sid_force(value, size, &newsid);
	}

即：context 里的 type 在策略中不存在（vendor_camera_remapid_prop 等）→ EINVAL →
退而求其次要 CAP_MAC_ADMIN 强制转换 → init 没有该权限 → mac_admin denied + setxattr
失败 → PropertyInit() 的 MUST 失败 → InitFatalReboot。类型一旦存在，这条路径根本不会走。

=== 3. 策略来源：init 加载的是 /odm 的预编译二进制，绕过了 patch 的 /vendor 策略 ===

官方 odm_a.img（out/roms/flyme/m22/12.5.0.0A/super/odm_a.img，782336 B）：
$ dump.erofs --ls --path=/etc/selinux odm_a.img
	 precompiled_sepolicy
	 precompiled_sepolicy.plat_sepolicy_and_mapping.sha256
	 precompiled_sepolicy.product_sepolicy_and_mapping.sha256
	 precompiled_sepolicy.system_ext_sepolicy_and_mapping.sha256

sha 校验必然通过（odm 记录 == system 现值）：
odm/etc/selinux/precompiled_sepolicy.plat_sepolicy_and_mapping.sha256
  = 797927f6c7c55f4414a8cf908f48d09ef22e2c094d36d1ec2876507e6a9b45fa
system/etc/selinux/plat_sepolicy_and_mapping.sha256
  = 797927f6c7c55f4414a8cf908f48d09ef22e2c094d36d1ec2876507e6a9b45fa

system 分区里没有任何预编译二进制（所以 init 不会在 /system 命中）：
$ dump.erofs --ls --path=/system/etc/selinux system_a.img    → 18 项，无 precompiled_sepolicy
$ dump.erofs --path=/system/etc/selinux/precompiled_sepolicy system_a.img → read inode failed

patch.img 的 /vendor/etc/selinux 也没有预编译二进制（lineage 侧清单）：
genfs_labels_version.txt / plat_pub_versioned.cil / plat_sepolicy_vers.txt(202504) /
selinux_denial_metadata / vendor_file_contexts / vendor_hwservice_contexts /
vendor_keystore2_key_contexts / vendor_mac_permissions.xml / vendor_property_contexts /
vendor_seapp_contexts / vendor_sepolicy.cil / vendor_service_contexts /
vendor_tee_service_contexts / vndservice_contexts

=> init 的候选顺序里 /system、/vendor 都空，命中 /odm 的二进制。

=== 4. 该二进制里没有 lineage vendor 侧声明的类型 ===

odm precompiled_sepolicy（1405958 B，magic 8cff7cf9）：
$ strings -a precompiled_sepolicy | grep -c "^vendor_qms_0$"              → 1   （官方 vendor 类型在）
$ strings -a precompiled_sepolicy | grep -c "^vendor_camera_remapid_prop$" → 0   （lineage 侧类型不在）

而运行时 /vendor（patch）的 vendor_property_contexts 却在用它们：
$ debugfs -R "cat /vendor/etc/selinux/vendor_property_contexts" patch.img | grep -n "remapid\|skip_failed\|partition_table"
75:vendor.create_partition_table.       u:object_r:vendor_create_partition_table_prop:s0
105:vendor.camera.remapid                  u:object_r:vendor_camera_remapid_prop:s0
108:vendor.camera.skip_failed_ids          u:object_r:vendor_camera_skip_failed_ids_prop:s0

这些类型在 patch 的 vendor_sepolicy.cil 里**有声明**（合并时会补上）：
$ debugfs -R "cat /vendor/etc/selinux/vendor_sepolicy.cil" patch.img | sed -n '748,749p'
(type vendor_camera_remapid_prop)
(roletype object_r vendor_camera_remapid_prop)
=> 问题不是「类型没人定义」，而是「声明在 cil 里，却被预编译二进制短路了，根本没参与编译」。

对照官方 flyme vendor（vendor_a.img）：vendor_property_contexts 510 行，**不含**这 3 个属性；
vendor_sepolicy.cil 1216306 B（17232 行）也不含这 3 个 type。官方是自洽的一对，
patch 的 /vendor 用的是 lineage 的精简 cil（319418 B）+ 带 flyme 私有属性的 property contexts，
只有走 cil 合并才能自洽。

=== 5. 排除项：plat_sepolicy_vers.txt 不是判定开关 ===

实验：把 patch.img 里 /vendor/etc/selinux/plat_sepolicy_vers.txt 由 "202504" 改成官方
flyme vendor 的 "202404"（同长就地覆盖，块 12148 偏移 49758208），新建实例 4：
$ cd out/core/daemon/runtime/m22_12.5.0.0A/4 && grep -E "SELinux policy|Compiling|precompiled" qemu.log
[    0.271519][    T1] init: Opening SELinux policy
[    0.274977][    T1] init: Loading SELinux policy
[    0.305346][    T1] init: Failed to initialize property area
行为完全不变 —— 仍然直接加载，说明版本号不是这条路径的开关（实验后已用 09 重出的
patch.img 覆盖，未留在产物里）。
