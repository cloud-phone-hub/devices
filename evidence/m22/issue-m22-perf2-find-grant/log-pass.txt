## B. 策略编译实证（按 init 同序，guest 内 secilc）

编译参数与 `cuttlefish/source/system-core/init/selinux.cpp:341-380` 一致：
`plat_sepolicy.cil -m -M true -G -N -c 30 -o <out> -f /sys/fs/selinux/null
plat mapping → system_ext → system_ext mapping → product → product mapping →
plat_pub_versioned → vendor_sepolicy.cil → (odm，缺则跳) → plat_sepolicy_genfs_202504.cil`。

| 试验 | 输入 vendor_sepolicy.cil | 结果 |
| :--- | :--- | :--- |
| 基线 | 机上旧策略（迁移前，机型层声明 perf2） | **RC=0**，869,038 B，sha256 `e84ee82f4ece057c…` |
| 中间态 | 本轮装配树原文件（含新模块块） | **RC=254**：`Failed to resolve permission nlmsg`，`Failed to resolve allow statement at …:2423` |
| 最终 | 装配树 + 清单 `patch.vendor-cil-rewrite` 四条规则改写（= 09 之后镜像里的文件） | **RC=0**，869,026 B，sha256 `db2b9f65b91a8651…` |

中间态的失败**不是** perf2 引起的：报错行 2423 是 lineage 自带的
`(allow ot_rcp self (netlink_route_socket (nlmsg)))`。本项目对它的处理是 09
`patch.vendor-cil-rewrite`（4 条规则，`from`/`to`/`count` 精确命中）：

```
#1 命中 1 次  (allow ot_rcp self (netlink_route_socket (nlmsg)))            -> nlmsg_write
#2 命中 1 次  (allowx ot_rcp self (nlmsg netlink_route_socket (0x16 …)))   -> 注释删除
#3 命中 1 次  (allowx ot_rcp self (nlmsg netlink_route_socket (0x12)))     -> 注释删除
#4 命中 1 次  (allow kernel_202504 vendor_firmware_file (system (firmware_load))) -> 注释删除
```

结论：**静态编译校验必须用 09 改写后的文件**，用装配树原文件会把「基底不可编译项」
误判成本条引入的问题（这条已写进 `solution.md` §6）。

## E. 同口径运行期对照（QEMU 串口全量流水，开机起）

取两边实例各自的 `out/core/daemon/runtime/m22_12.5.0.0A/<index>/qemu.log`，
按「结构完整的 avc 记录」统计（口径与 `log-fail.txt` D 段同一套：kernel `SELinux: avc:`
与 logd `auditd` 两路上报都算），统计时刻两份日志已用 sha256 钉住：
37 = `62e9ab4aad3cd84b…`（已停机）、38 = `e9754a00b2e658a9…`。

| 实例 | 策略 | `denied { find }`（tclass=service_manager） | `Could not find … in the VINTF manifest`（= 查询被放行） | 日志跨度（kernel tsc） |
| :--- | :--- | ---: | ---: | :--- |
| 37 | 迁移前（机型层只有 system_server/lmkd） | **1554**（kernel 454 + auditd 1100，跨 19 个域） | 830 | 0.000 → 3162.535 s（52.7 min） |
| 38 | 迁移后（模块层 + `domain` 通配） | **0** | **1219** | 0.000 → 1091.164 s（18.2 min） |

- 提示数 1219 > 830 说明迁移后**查询量更大**（新镜像开机阶段 app 冷启更多），
  在这种更高的查询量下 denied 仍为 0 —— 不是「没人查」的假绿。
- 提示本身是 servicemanager 正常回话：名字有标签、find 通过、但 VINTF 未声明
  实例，所以按「不可用」降级。它是「查询确实发生且被允许」的正向证据。
- 两列数字随实例运行会缓慢增长（38 在写文档时仍在跑），本文用「同一时刻两份文件」
  作对照；宽松同行匹配（`grep -a -c`）同一时刻为 837 / 1232，量级关系一致。
- **口径更正**：此前 E 段写作 1600 / 0（行级 `scontext` 归属），会把串口拼接进来的
  别的 avc 的域算给 perf2，已改为记录级抽取；也不再声称「`grep` 不带 `-a` 会大幅
  漏计」——复测未能复现，带 `-a` 仅为规避控制字节的稳妥写法。
- **为什么 38 不是「没东西可查」**：38 的日志里仍有 24 行同时含 `perf2.IPerf` 与
  `avc:`，逐条看全是 `pioneer` 跑 `pidof` 时被拒的 `{ read }` / `{ search }`
  （另一些 avc 与它拼在同一行），与 perf2 服务名无关；按记录级正则一条也不匹配，
  所以 `denied { find }` 为 0 是真的没有发现拒绝，而不是筛选条件把它们排除了。

## F. 事后窗口（logcat ring buffer，验证「无回归」）

- 采集：12,971 行，其中 `avc:` **608** 行；含 `perf2` 的行 **0** 行
  （`denied { find }` 0、`tclass=service_manager` 0）。
- 同一窗口内 `Could not find … perf2 … VINTF manifest` 也是 **0** 条：说明这批
  `monkey` 触发并没有再走 perf2 查询路径（框架侧已按「不可用」缓存），所以本窗口
  只作为「无新增 denied」的补充，查询侧结论以 E 段为准。
