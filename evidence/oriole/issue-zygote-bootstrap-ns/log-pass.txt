## 判定
- vdc 在 0.269 s 以 first_stage_mount 挂到 /mnt/vendorpatch：__mount(...)=0: Success；
- vold 的 3 个指标全为 0：Found map 0、Tearing down stale mount 0、Sending Interrupt 0
  （对比实例 2 的 131 / 4），载体不再被当 stale mount；
- avc mnt_vendor_file 0 条（对比实例 3 的 3924 条），落点不在 /mnt/vendor/ 之下；
- cdh_redirect 生效 1250 次，目标全是 /mnt/vendorpatch/…；
- apexd.status=activated 在 5.390 s 就绪（Wait 1763 ms），zygote/system_server 起来后
  system_server 已跑到 StartActivityManager。

## 后续卡点（不属于本 issue，另行闭环）
本实例仍在 31.7 s 触发 init 的 "process with updatable components
'vendor.hwcomposer-3' exited 4 times before boot completed" → 重启进 recovery，
sys.boot_completed 始终为空。原因是 /vendor/bin/hw/android.hardware.composer.hwc3-service.drm
在 Android 14 底座上找不到 std::__1::__libcpp_verbose_abort 与
AIBinder_Class_setTransactionCodeToFunctionNameMap 两个符号，它的 rc 里
onrestart restart surfaceflinger 又把 main 类整体拉崩。与本 issue 的载体落点无关：
本实例下 vold 对载体的 0 次干预已经证明落点问题解决。
