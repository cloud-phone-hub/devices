## D. 本轮第一次 07 实跑：现编 compat 库选中了 `ndk/magisk`

来源：`/tmp/cdh-07/run.log`（第一次实跑，2026-11-01 13:52，`EXIT=0` 但产物来自非预期编译器）。

```
    composer compat: 现编（/Users/cuimingqiang/Library/Android/sdk/ndk/magisk/toolchains/llvm/prebuilt/darwin-x86_64/bin/clang++）
        -> out/devices/google/oriole/AP2A.240905.003.F1/vendor/lib64/libcdh_composer_compat.so
    composer 依赖: DT_NEEDED android.hardware.graphics.composer@2.2-resources.so -> libcdh_composer_compat.so
```

`~/Library/Android/sdk/ndk/` 下除了 `26.0.* / 26.1.* / 28.0.* / 28.2.* / 29.0.*` 这些版本目录，还躺着一个
`magisk/`（顺手放的目录）与 `.zip` / `.tar.xz` 安装包。第一版 `locateNDKClang` 按目录名字典序取最大，
`magisk` 恰好排在数字版本之后 → 被选中。装配不报错、compat 库照样产出，**只有日志里那一行能看出来**。

修复：`ndkVersionsDesc` 把「以数字开头」的目录排前面（新版本在前），其余排后面；重跑后选中 `29.0.14206865`。

## E. 运行期原始报错（旧静态树 / 中间态的实证）

这两条不是本轮产生的日志，而是驱动这次改造的运行期证据，引自本条关联条目与机型基线 `note`：

1. 中间态把 libui 及其私有依赖放进临时树、`from` 还没配好时，`vendor` 命名空间取不到 `/system/lib64` 那份（libui 不在 A14 LLNDK 名单）：

```
CANNOT LINK EXECUTABLE "/vendor/bin/hw/android.hardware.composer.hwc3-service.drm":
library "libui.so" not found: needed by main executable
```

2. 更早一轮：A15 库 `BIND_NOW`，A14 运行库缺两个符号，`dlopen` 直接失败（详见 #101 遗留与 #102；
   下面两行是**归纳**而非本条实跑日志原文，符号名取自 `llvm-nm -D --undefined-only`）：

```
cannot locate symbol "_ZNSt3__122__libcpp_verbose_abortEPKcz"                 # 被 composer3-V4-ndk / graphics.common-V6 等引用
```

## F. 一句话

三条现场合起来说明：**「有字节、无出处」的静态树在换基座、换 NDK、换机器之后无法自证**——
把 16 件挪进清单（15 条借件 + 1 条现编）之后，每件都能在执行计划里看到来源路径。
