== 7) 当时的结论（已被第 8 节推翻，保留原文备查）==
触发条件是**内核 console 日志级别**：loglevel=7 时 30 秒内 binder async 池就被打满；
loglevel=4 时同样的交互负载下 ENOSPC / oneway spam / FATAL 全为 0。
但池子一旦打满就不可逆，事后压回 4 也救不回来 —— 必须开机第一时间生效。
`/proc/sys/kernel/printk` 不是持久设置，重启即失效，当前只算临时缓解。

→ 推翻依据：11:35 那轮已在 boot+53 s 设为 4，仍于 11:44 崩（ENOSPC 72 / spam 384 /
  DeadSystem 1442）。loglevel 只是把崩点从开机 323 s 拖到 434 s 以上，不是根因。

== 8) binder 层定因：SF RegionSampling → system_server 的 async 积压（12:20–12:45）==

前提：debugfs 挂上后直接读 binder 内部（adb shell 权限不够，走 hvc7 root 通道）。

-- 8.1 身份 --
$ cat /proc/582/comm           -> surfaceflinger
$ cat /proc/582/task/682/comm  -> RegionSampling        ← 发送方
$ cat /proc/769/comm           -> system_server         ← 目标

-- 8.2 唯一的异常进程 --
$ grep 'free async space' /sys/kernel/debug/binder/stats | sort | uniq -c | sort -rn
    155   free async space 520192      ← 其余全部满额
      1   free async space 273888      ← 769 system_server，约 47% 已用（240848→250368→252608→273888，回升）

-- 8.3 pending 全部同形 --
$ grep -c 'pending async' /sys/kernel/debug/binder/proc/769     -> 941
$ ... | sed 's/.*from \([0-9]*\):[0-9]* to \([0-9]*\):[0-9]* code \([0-9]*\) .*size \([0-9]*\):.*/from\1-to\2-code\3-size\4/' | sort | uniq -c | sort -rn
    471 from582-to769-code2-size436
    471 from582-to769-code1-size92
  → 100% 来自 surfaceflinger，严格成对，没有第二个来源

-- 8.4 队首从开机起没被消费 --
pending async transaction 105409: … from 582:682 to 769:0 code 1 flags 11 pri 0:120 r0 elapsed 1254470ms node 9312 size 92:0  offset 22a18
pending async transaction 105410: … from 582:682 to 769:0 code 2 flags 11 pri 0:120 r0 elapsed 1254470ms node 9312 size 436:24 offset 22a78
node 9312: … ls 943 lw 0 is 1 iw 1 tr 1 proc 582        ← ls 943 ≈ pending 942，每个未消费事务各持 1 个 strong ref

-- 8.5 队列在动，但只勉强持平 --
30 秒差分（按事务 id）：918 → 912 条，消费 12（全在队首，id ≤104527）、新增 6（id 148475）
→ FIFO 在推进（≈0.4 条/s），深度常年 900 上下，队首永远是开机时刻的事务。

-- 8.6 记账 --
520192 B 池子 / 528 B 每对 ≈ 985 对打满；当前 450 对 ≈ 246 KB（= 520192−273888 ✓）

-- 8.7 本轮存活情况（12:09:17 起，boot+59 s 设 printk=4）--
12:27   enospc 0 / spam 0 / DeadSystem 0，mCurrentFocus=com.meizu.connectivitysettings/.Settings
12:45   同上，已连续存活 >35 min（超过之前所有崩点）
→ 结论：不是「必崩」，而是「净增长率 > 0 才崩」。

== 9) 结论 ==
1. 真正机制：surfaceflinger 的 RegionSampling 线程每秒一对 oneway 通知 system_server，
   system_server 侧消费速度只勉强持平（队首常驻 20 分钟）；一旦生产略快（负载/日志背压/
   调度抖动），队列单调增长至 985 对打满 512 KiB async 池 → -28 ENOSPC → DeadSystem 风暴 → 冻结。
2. console loglevel 是加速器：它压低消费速度，把「持平」变成「落后」。
   loglevel=4 能延后崩点（323 s → 434 s+），但不能清零。
3. 池满不可逆，只能重启进程（/api/stop + /api/start）。
4. 待闭环：code1/code2 对应的 AIDL 接口，以及运行态关掉内容采样后 pending 是否归零（见 solution.md 第 6 节）。

== 10) 决定性 A/B：自动亮度 ON/OFF 就是这条洪泛的开关（12:37–12:44）==

指纹：取「最新一条 pending 的 elapsed」——生产停了它会跟着墙钟长，生产在跑它就重新变小。
$ D=/sys/kernel/debug/binder/proc/769
$ grep -o "elapsed [0-9]*ms" $D | awk "{print \$2+0}" | sort -n | head -1

基线（settings get system screen_brightness_mode -> 1）
  最新 29407ms      pending 941
$ settings put system screen_brightness_mode 0
  即时            最新 171001ms   pending 762
  +120 s          最新 291042ms   pending 714     ← 恰好 +120 s，零新增 → 生产停了
$ settings put system screen_brightness_mode 1
  +90 s           最新  50419ms   pending 676     ← 重新变小 → 生产立即恢复
$ settings put system screen_brightness_mode 0     # 收尾保留关闭
  pending 666   free async space 333248（273888 → 333248，继续回落）

同期系统健康（12:44:27）：
  cannot allocate buffer = 0 / spamming oneway = 0 / DeadSystem = 0
  mCurrentFocus = com.meizu.connectivitysettings/.Settings

→ 最终结论：
  ① 洪泛源：自动亮度 → SF 内容采样 → RegionSampling 每秒一对 oneway 给 system_server；
  ② 打满条件：system_server 消费只有 ≈0.4 条/s 而 SF 投递 ≈2 条/s，净增长 > 0 就崩；
  ③ 加速器：console loglevel=7 + seriallogging=hvc1 + 三个缺失 HAL 每秒重试；
  ④ 落地建议：镜像层默认关闭自动亮度（云机无环境光传感器），再叠 loglevel=4。
