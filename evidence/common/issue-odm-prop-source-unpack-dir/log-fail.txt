== 06 的 odm 属性件留档目录名写死 unpack_vendor：跨分区撞车，odm 层把 vendor 收口全盖回（2026-11-04，cph2797 实例 2）==

前置：本轮实例 1 的 FRP 卡点已修（#153），system_server 越过 phase 500，引导才走得到渲染侧。
实例:  out/core/daemon/runtime/cph2797_16.0.8.301_EX01/2
构建:  engine/out/tmp/cph2797-build2.log（07 已单独跑过，unpack_vendor 树在位）
判定:  engine/out/tmp/cph2797-boot-check2.log
       [fail] 超时 600s 未出现 sys.boot_completed=1（当前日志 49976 行）


## 1. 同一台机、同一条命令，两次读到的「厂商 odm 原件」不是一回事

$ grep -n "厂商原件:" engine/out/tmp/cph2797-build.log engine/out/tmp/cph2797-build2.log
cph2797-build.log:521:    厂商原件: .../super/unpack_vendor/build.prop（138 行 / sha256 0606e97aa3aa）
cph2797-build2.log:21:   厂商原件: .../super/unpack_vendor/build.prop（917 行 / sha256 6af1959e68ad）

run1 时 `<super>/unpack_vendor/` 还是空的，06 自己把 odm_a.img 的 /build.prop 解进去，
内容恰好是真 odm 件（138 行）→ 产物正确（纯属侥幸）。
run2 之前 07 步骤 1b 把厂商 **vendor_a.img 整树**解到同名目录，那里躺着 917 行的
vendor build.prop；06 按「留档优先」直接读它 → 产出的 odm/etc/build.prop 成了 vendor 的副本：

$ grep -n "生成 odm 覆盖件" -A1 engine/out/tmp/cph2797-build2.log
27:==> [步骤 1] 生成 odm 覆盖件 -> out/devices/oppo/cph2797/16.0.8.301_EX01/odm/etc/build.prop
28:    abilist32="" abilist64=arm64-v8a sha256=922 行 / sha256 a3f0ad343852
        ↑ 138 行的 odm 原件不可能撑出 922 行产物；922 = vendor 917 + 5 条 odm sets 追加

（官方 odm_a.img 的 /build.prop 只有 138 行，且不含任何 GPU 后端键：
 engine/out/tmp/cph2797-official-odm-build.prop 为 dump.erofs --cat 取出的原件留档）

$ grep "Overriding previous property" out/core/daemon/runtime/cph2797_16.0.8.301_EX01/2/qemu.log \
    | sed 's/.*init: //' | sort -u | grep -E 'egl|hwcomposer|use_vulkan|opengles'

Overriding previous property 'ro.hardware.hwcomposer':'drm' with new value 'mtk_common'
Overriding previous property 'ro.hwui.use_vulkan':'false' with new value ''
Overriding previous property 'ro.hwui.use_vulkan':'' with new value 'true'

（前四行方向都是「基线收口值 → 厂商原值」：/vendor/build.prop 的收口白做了；
 use_vulkan 出现两次是因为 vendor 副本里那两行重复键也被整份搬进了 odm 层）
